為什麼開始做

臨床資料與裝置事件需要可信邊界，但同時必須適應醫療現場的時間壓力。

系統簡介

此系統以醫療紀錄與裝置事件流程作為原型情境，用來整理身分驗證、權限控制、裝置信任、稽核紀錄與異常回報之間的關係；目前仍屬個人研究準備與工程原型，不代表正式臨床部署。

我的角色

System design, backend implementation, security workflow, and device integration

系統層級

前端介面 後端 API 裝置通訊 身分驗證 權限控制 稽核紀錄 異常事件回報

現在遇到的問題

錯誤權限

系統簡介
使用者嘗試執行不符合角色權限的操作。
排查
檢查 API 權限檢查與 RBAC 規則。
處理方式
將權限失敗納入測試與稽核紀錄。
目前驗證
部分完成
學到的內容
權限錯誤應被明確拒絕並留下可追蹤紀錄。

訊息重送

系統簡介
裝置或攻擊者重送先前的有效訊息。
排查
檢查簽章、時間或序號假設。
處理方式
將重送防護列為裝置通訊設計重點。
目前驗證
整理中
學到的內容

裝置離線

系統簡介

排查
檢查 MQTT 流程與裝置狀態回報。
處理方式
將離線狀態列入後續測試。
目前驗證
需要更多測試

已有解決方案

分離使用者身分與裝置信任

原因
使用者登入成功不代表裝置訊息可信。
取捨
需要額外設計裝置簽章、金鑰與重送防護。

保留稽核紀錄

原因
醫療與安全情境需要能追蹤誰在何時做了什麼。
取捨
必須控制紀錄內容，避免保存過多敏感資料。

先做可運作原型

原因
原型能用來驗證流程與安全假設。
取捨
不能把原型描述成正式產品或臨床部署。

尚未解決的問題

  • Clinical workflow assumptions need careful validation
  • Private implementation details must be sanitized before public release

限制

  • 目前是工程原型，不是正式醫療系統。
  • 尚未完成臨床部署、使用者測試與正式資安評估。
  • 裝置金鑰管理與韌體安全仍需深化。
  • 稽核紀錄尚未完成防竄改與長期保存設計。
  • 公開文件需要移除內部實作與敏感脈絡。

學到的內容

  • 安全控制必須符合時間壓力下的使用流程。
  • 身分驗證、授權、裝置信任與稽核紀錄需要分層設計。
  • 原型可以驗證假設，但不能取代正式測試。
  • 公開成果需要清楚區分證據、限制與未完成項目。

研究觀點

研究 / 工程問題
如何在降低護理紀錄負擔的同時，保留身分驗證、裝置可信度、稽核與異常回報能力？

子問題

  • 如何在不增加過多操作負擔下保留身分驗證與稽核紀錄？
  • 如何判斷裝置回報是否可信？
  • 如何處理重送訊息、錯誤權限與裝置離線？
  • 哪些資料可以公開作為證據，哪些必須保持 private？

後續工作

整理威脅模型 補齊測試證據 設計更清楚的裝置信任流程 區分公開文件與 private implementation details 探索醫療資訊安全與臨床流程的交界

下一步

整理可公開的架構文件、威脅假設與測試證據，並分離 private implementation details。
